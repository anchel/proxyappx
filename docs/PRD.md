# ProxyAppX 产品需求文档（PRD）

> 版本：v1.0　｜　平台：macOS 15 及以上（Apple Silicon / Intel）　｜　状态：已实现首版

## 1. 背景与问题

macOS 的「系统代理」是全局的，而且只对主动读取系统代理设置的程序生效：

- 很多应用（Electron 应用、游戏、命令行工具、自带网络栈的客户端）**完全不理会系统代理**；
- 一旦开了全局代理，**所有应用**的流量都会走代理，没法做到「只让某几个应用走代理」；
- 现有的 TUN 模式工具大多按域名或 IP 分流，**不按应用分流**，配置也重。

**ProxyAppX 要解决的问题：用户选中某个应用，这个应用的全部网络流量就从指定的代理服务器出去，其他应用不受影响。**

## 2. 目标用户与典型场景

| 场景 | 描述 |
| --- | --- |
| 开发者 | 只让 Xcode、Cursor、终端里的 `git` / `curl` 走公司代理，其他照常直连 |
| 办公 | 只让 Slack、Teams 走指定线路，浏览器保持直连 |
| 游戏 / 下载 | 让某个游戏客户端或下载器走专用的 SOCKS5 线路 |
| 隐私隔离 | 某个应用**禁止联网**（阻断），或强制只走代理（代理挂了就断网，不泄漏） |
| 排除模式 | 默认所有应用都走代理，只让少数应用（如国内应用）直连 |

## 3. 产品目标

1. **按应用**精确分流：同一个应用的主进程、helper 子进程（如 Chrome Helper、Electron Helper）都能识别到。
2. **零侵入**：不改应用、不注入代码、不需要应用本身支持代理。
3. **不泄漏**：默认对走代理的应用采用 fail-closed，并默认阻断其 UDP（迫使 QUIC 回落到 TCP），避免绕过代理。
4. **好上手**：选应用 → 选代理 → 打开开关，三步就生效；状态、连接和流量都看得见。

### 非目标（v1 不做）

- 按域名 / IP 规则分流（后续版本见第 9 节）
- DNS 代理 / Fake-IP（DNS 仍由系统解析，见「已知限制」）
- Shadowsocks、VMess、Trojan 等加密协议（可以先用本地客户端开 SOCKS5 端口，再交给 ProxyAppX 转发）
- 代理链、负载均衡、iOS 版本

## 4. 功能需求

### F1 代理服务器管理
- F1.1 支持 **SOCKS5**（RFC 1928），支持无认证和用户名 / 密码认证（RFC 1929）。
- F1.2 支持 **HTTP 代理**（`CONNECT` 隧道），支持 Basic 认证。
- F1.3 可以添加多个服务器，每个服务器包含：名称、类型、主机、端口、用户名、密码（存在钥匙串里）。
- F1.4 SOCKS5 服务器可以勾选「支持 UDP 转发」（UDP ASSOCIATE）。
- F1.5 **连通性测试**：经该代理连接一个测试地址（默认 `www.apple.com:443`），显示握手耗时或失败原因。
- F1.6 删除服务器时，如果还有规则在引用它，要提示，并把这些规则改为「直连」。

### F2 应用规则
- F2.1 添加应用的三种方式：从「应用程序」文件夹选 `.app`；从「正在运行的应用」列表里选；选任意可执行文件（命令行工具，如 `/usr/bin/curl`）。
- F2.2 每条规则包含：应用（名称、图标、Bundle ID / 签名标识、路径）、**动作**、UDP 策略、启用开关。
- F2.3 动作分三种：**代理**（需选择代理服务器）/ **直连** / **阻断**。
- F2.4 UDP 策略（仅动作为「代理」时生效）：
  - **阻断**（默认）：浏览器的 QUIC/HTTP3 会自动回落到 TCP，确保不泄漏；
  - **直连**：UDP 不经过代理；
  - **经 SOCKS5 转发**：需要服务器支持 UDP ASSOCIATE；如果服务器是 HTTP 代理，就按「阻断」处理并记日志。
- F2.5 规则可以单独启用或停用，也可以搜索。

### F3 匹配语义（核心）
每个新连接都会带上来源进程的**签名标识**和**可执行文件路径**，按下面的优先级匹配（数值越大越优先）：

| 优先级 | 条件 | 例子 |
| --- | --- | --- |
| 3 | 签名标识与规则的 Bundle ID **完全相等** | `com.google.Chrome` |
| 2 | 进程路径等于规则路径，或位于规则应用的 bundle **内部** | `/usr/bin/curl`、`/Applications/Slack.app/Contents/Frameworks/Slack Helper.app` |
| 1 | 签名标识以 `规则ID.` 为前缀 | `com.google.Chrome.helper` |

- 多条规则都命中时，取优先级最高的；优先级相同时，取 Bundle ID 更长（更具体）的那条。
- 都没命中时，执行**默认动作**（设置项，默认「直连」）。
- **始终直连**（不受规则影响）：
  - 环回地址（127/8、::1、localhost）；
  - 开启「绕过局域网」（默认开启）时：私有网段、链路本地、CGNAT、组播、`.local`（10/8、172.16/12、192.168/16、169.254/16、100.64/10、fc00::/7、fe80::/10）；
  - 目标恰好是某个已配置的代理服务器（防止二次代理）；
  - 系统 DNS 解析器 `mDNSResponder`，以及所有发往 53 端口的 DNS 查询（系统会把 DNS 查询归属到发起解析的应用；如果按该应用的 UDP 策略阻断，它就无法解析域名）。
- **系统进程豁免**（默认开启）：默认动作不是「直连」时，Apple 签名且位于 `/System`、`/usr`、`/bin`、`/sbin` 等目录下的进程，只要没被规则显式命中，就仍然直连，避免系统更新、iCloud、证书校验等服务被误伤。

### F4 全局设置
- F4.1 **总开关**：启用或停用分流（对应系统里的透明代理配置）。
- F4.2 **默认动作**：未命中规则的应用走「直连」或「代理（选一个服务器）」。后者就是「排除模式」。
- F4.3 **代理不可用时**：`阻断`（fail-closed，默认）/ `回落直连`（fail-open）。回落只对 TCP 生效；UDP 关联失败时一律阻断（应用通常会自动回落到 TCP）。
- F4.4 **优先使用域名连接代理**（默认开启）：如果系统提供了连接的目标域名，就把域名交给代理解析，否则发送 IP。
- F4.5 **绕过局域网**（默认开启）。
- F4.6 **登录时启动**。
- F4.7 配置可以**导入 / 导出**为 JSON（导出时不含密码）。
- F4.8 **系统进程仍然直连**（默认开启，仅在默认动作不是「直连」时出现），见 F3。
- F4.9 **连接超时**：3–60 秒，默认 10 秒。

### F5 状态与监控
- F5.1 概览页：系统扩展状态（未安装 / 待批准 / 已启用）、代理开关状态、活动连接数、累计上下行流量。
- F5.2 **实时连接列表**（每秒刷新）：应用、目标地址（域名:端口）、协议、动作或代理、上行 / 下行字节、持续时间。
- F5.3 **日志**：最近 500 条事件（规则命中、代理握手失败、阻断等），可以按级别过滤，也可以清空。
- F5.4 **菜单栏图标**：显示开启或关闭状态，可以一键切换、打开主窗口、退出。
- F5.5 **未匹配的应用**：列出最近联网、但没命中任何规则的进程（按签名标识聚合，显示连接数和最近目标），可以一键为它创建规则（自动归并到所属的 .app）。这样用户能发现某个应用的 helper 进程，也能排查「为什么这个应用没走代理」。

### F6 安装引导
- F6.1 首次启动时引导用户：安装系统扩展 → 到「系统设置 › 通用 › 登录项与扩展」里允许 → 允许添加代理配置。
- F6.2 每一步都显示当前状态，出错时给出可操作的提示（例如「请把 App 移到 /Applications」）。

### F7 与其他 VPN / TUN 工具共存（Clash、FlClash、Surge、公司 VPN 等）
ProxyAppX 在 socket 层先看到连接；它放行的流量（含 DNS）交还给系统网络栈后，照常按路由进入其他 TUN 工具。在此基础上：
- F7.1 **绑定网卡的连接直连**（默认开启）：应用把连接绑定到网卡（`NEAppProxyFlow.isBound`）时一律放行。代理内核用这种方式绕开自己的 TUN，接管后会丢失绑定、形成回环。
- F7.2 **fake-IP 兜底**（默认开启）：目标位于 198.18.0.0/15、又拿不到域名，且上游代理不在本机时，放行给制造 fake-IP 的 TUN 工具处理（远程代理无法连接 fake-IP）。只要有域名，即使关闭了 F4.4，也一定把域名交给代理。
- F7.3 **上游连接绕过其他 VPN / TUN**（默认关闭）：扩展连接上游代理时禁止使用 utun 等网卡，直接走物理网卡，避免被 TUN 工具二次代理。代理服务器只能经公司 VPN 访问时不能开启。
- F7.4 **检测与提示**：检测承载公网流量的网卡是否为 utun 等隧道网卡，以及是否处于 fake-IP 模式；可能二次代理或回环时在概览页提示，并提供可复制的 Clash 规则 `PROCESS-NAME,com.proxyappx.app.extension,DIRECT`。

## 5. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 规则匹配 O(规则数)，进程信息按 audit token 缓存；转发采用流式读写，带背压，单连接缓冲 ≤ 64 KB |
| 稳定性 | 连接超时 10 秒，握手超时 10 秒；单个连接出错不影响其他连接；扩展崩溃后由系统自动拉起，从持久化配置恢复 |
| 安全 | 密码存在钥匙串；只在启动或更新配置时下发给扩展；默认 fail-closed；扩展运行在沙盒中 |
| 隐私 | 不上传任何数据；日志只保存在内存里（扩展重启即清空） |
| 兼容 | macOS 15+；同时支持 IPv4 / IPv6 |

## 6. 技术方案

### 6.1 为什么选 Network Extension 透明代理
| 方案 | 能否按应用 | 能否覆盖不理会代理的应用 | 结论 |
| --- | --- | --- | --- |
| 设置系统代理 / 环境变量 | ✗ | ✗ | 不可行 |
| DYLD 注入 | ✓ | 部分 | 被 SIP 和 Hardened Runtime 阻止，不可行 |
| pf 防火墙 + 重定向 | ✗（无法按进程） | ✓ | 不可行 |
| **NETransparentProxyProvider（系统扩展）** | ✓（每个 flow 带来源进程签名和 audit token） | ✓（工作在 socket 层） | **采用** |

### 6.2 架构

```
┌──────────────────────────── ProxyAppX.app（用户态，SwiftUI）────────────────────────────┐
│  配置 UI / 菜单栏  ── ConfigStore(JSON + 钥匙串)  ── ProxyController(NETransparentProxyManager)│
│  ExtensionManager(OSSystemExtensionRequest)        ── IPC: sendProviderMessage(JSON)          │
└──────────────────────────────────────────┬──────────────────────────────────────────────────┘
                                           │ providerConfiguration（持久化）+ 实时消息
┌──────────────────────────────────────────▼──────── ProxyAppX Extension（root，系统扩展）─────┐
│ TransparentProxyProvider                                                                   │
│   handleNewFlow / handleNewUDPFlow                                                          │
│     → ProcessResolver(audit token → 可执行文件路径)                                          │
│     → RuleEngine.decide() → 直连(return false) / 阻断 / 代理                                  │
│     → TCPRelay(flow ⇄ ProxyConnector: SOCKS5 / HTTP CONNECT / Direct)                        │
│     → UDPRelay(flow ⇄ SOCKS5 UDP ASSOCIATE)                                                  │
│   ConnectionTracker(连接、流量、日志) ← getStatus 查询                                         │
└────────────────────────────────────────────────────────────────────────────────────────────┘
                    ProxyAppXCore（Swift Package，被以上两者共享，带单元测试和集成测试）
```

- **直连的流量**：`handleNewFlow` 返回 `false`，由系统原样处理，零开销。
- **扩展自身发出的连接**不会被再次拦截，因此连接代理服务器不会形成回环。
- **配置下发**：App 把完整配置（含密码）写入 `NETunnelProviderProtocol.providerConfiguration`，扩展启动时读取；运行中修改配置时，再通过 `sendProviderMessage` 热更新，无需重启。

### 6.3 签名与分发要求
- 需要加入 Apple Developer Program，并给 App ID 开通 **Network Extensions** 和 **System Extension** 能力。
- Developer ID 分发时，entitlement 的值为 `app-proxy-provider-systemextension`，开发签名时为 `app-proxy-provider`。
- App 必须放在 `/Applications` 下才能激活系统扩展；对外分发还需要公证（notarize）。

## 7. 已知限制

1. **DNS 不经过代理**：系统会把应用通过 `getaddrinfo` 等接口发出的 DNS 查询（53 端口）归属到该应用。为了不让「阻断 UDP」等策略导致应用无法解析域名，DNS 查询一律直连。缓解办法是开启 F4.4，把域名交给代理远程解析，这样连接本身仍然走代理。
2. **共享系统进程**：Safari / WebKit、`nsurlsessiond` 后台下载等由系统进程代发的流量，归属取决于系统的归因，可能无法精确匹配。
3. **排除模式的回环风险**：如果默认动作是「代理」，而代理客户端（如 Clash）就在本机运行，必须给这个客户端加一条「直连」规则，否则会形成回环。UI 会在这种配置下给出警告。
4. **凭据存放**：v1 把代理密码写在系统的 NE 配置里（只有 root 可读写的系统偏好）；v1.1 计划改为系统钥匙串引用。
5. **TUN 工具的系统代理模式**：如果 Clash 类工具开启了「系统代理」，遵守系统代理的应用会连 `127.0.0.1:7890`，ProxyAppX 看到的是环回地址，一律放行，该应用的 ProxyAppX 规则不会生效。TUN 模式没有这个问题。
6. **进程路径解析**：扩展运行在沙盒中，如果系统拒绝解析某个进程的路径，只能按签名标识匹配（完全相等或前缀），路径匹配会失效。

## 8. 验收标准

- [ ] 添加 `curl` 规则走 SOCKS5 后，`curl https://ifconfig.me` 返回代理出口 IP，而 Safari 访问同一地址返回本机 IP。
- [ ] Chrome 规则生效后，Chrome Helper 的连接显示在连接列表里，并归属于 Chrome 规则。
- [ ] 代理宕机且策略为「阻断」时，被代理的应用连接失败；策略为「回落直连」时能正常上网。
- [ ] 规则设为「阻断」后，该应用所有连接立即失败。
- [ ] 修改规则后不用重启，新建的连接立刻按新规则走。
- [ ] 局域网地址（如 192.168.1.1）在「绕过局域网」开启时直连。
- [ ] 核心模块单元测试和集成测试（SOCKS5 / HTTP 握手、UDP 封包、规则匹配）全部通过。
